# Operations reference

Configuration and service details for running Captab. The [README](../README.md) gives the overview and evidence; the [runbook](RUNBOOK.md) gives the deployment sequence.

The company overview links to dedicated `/ownership`, `/grants`, `/approvals`, and `/distributions` workflows, with grant and distribution detail pages. `/me` shows the connected account's holdings, claims, and entitlements; `/activity` shows tracked receipts and DAO proposals.

The approvals workflow also prepares DAO pause, resume, and unfunded-distribution cancellation proposals from current chain state. Resume and unfunded cancellation remain available while the company is paused; payment callbacks continue settling existing attempts.

Rust is pinned to 1.88.0 in `rust-toolchain.toml`; pnpm is pinned to 10.16.1. Run unit tests with `pnpm test:contract`, schedule tests with `pnpm test:vesting`, and full chain tests with `pnpm test:sandbox`. The sandbox script fetches official Sputnik DAO source at commit `5434a59dec23ee0c49df8c8c4350c208a7e75b0b`, builds it with Rust 1.88.0, and verifies the WASM SHA-256 `a6055ab340bb5b9909ce4ff4bc7d2ae365b77d7b4b74d481fc2d2ee97c8a0722`. The Sandbox failed-callback case builds a separate fault-injection company WASM; deployment scripts reject that artifact. Build the normal company WASM with `pnpm build:contract`. After `pnpm --dir apps/web build`, run `pnpm test:worker-restart` to rehearse persistent payment recovery across a production-server and worker restart. Install frontend dependencies with `pnpm install`, then run it with `pnpm --filter @captab/web dev`.

The testnet runbook includes `pnpm freeze:company` for a read-only deployment-key removal preflight. Its `--apply` mode is reserved for the reviewed final release; `pnpm verify:testnet --require-frozen` checks that no full-access key remains afterward.

The [Sandbox storage stress test](STORAGE_LIMITS.md) measures 518,478 bytes for a company at the demo's holder, grant, distribution, and action limits, including contract code, and verifies a payout callback at those limits. The public company config exposes schema version 1 and those immutable limits for setup and deployment verification.

The setup and distribution screens read the DAO's current settlement-token balance alongside the proposed funding budget. If that token view is unavailable, the balance is labeled unavailable while the company's authoritative ledger and distributions remain visible.

After testnet deployment, set `CAPTAB_COMPANY_CODE_HASH` to `company.codeHash` from the deployment manifest. The app verifies the deployed company code before enabling governance, claims, sponsorship, or payment execution; read-only ledger views remain available if that check fails.

The app also checks the configured NEAR RPC node's chain ID before reading company state or preparing writes. A mainnet or unavailable RPC endpoint fails closed instead of being treated as testnet.

GitHub Actions runs the pnpm web tests, Chromium browser tests, production build, Rust contract tests, and the Sandbox lifecycle on pushes and pull requests. Run the local browser suite with `pnpm --filter @captab/web exec playwright install chromium` once, then `pnpm test:e2e`; it starts a fixture NEAR RPC and Next.js server on loopback. The pnpm workspace explicitly permits the native build steps used by `better-sqlite3` and `sharp` so a clean install can exercise the same checks.

`GET /api/companies/<account>` reads all bounded on-chain grants and distributions, checks supply and funded-escrow arithmetic, and reports the local history observation counts and last final observation. The worker repeats the chain audit for known companies at least every five minutes and saves its last result for the activity page. A changed ledger revision during reads yields an inconclusive audit that should be retried. History coverage remains limited to app-submitted transactions; audit consistency does not imply external activity has been indexed.

For the local activity service, copy `apps/web/.env.example` into a local environment file, set a random `CAPTAB_WORKER_SECRET`, and run the web app and `pnpm --filter @captab/web reconcile:worker` in separate terminals. `CAPTAB_DB_PATH` defaults to a local `.data/captab.sqlite` file. The observation endpoint checks that an included transaction's hash, signer, and receiver match the company or its DAO before storing it. The worker retries pending tracked transactions at finality and stores receipt IDs, block hashes, execution status, and deduplicated `captable` events from successful company receipts. A failed or unknown company receipt leaves its tracked operation in `NeedsReview`. Finalized DAO submissions are linked to their proposal IDs and action IDs; the worker checks later DAO status and flags a payload mismatch. DAO approval alone is not proof that the company call succeeded, so the activity page also links finalized receipts and contract views. The activity page intentionally covers app-submitted transactions only; externally submitted actions require a separate history provider. SQLite assumes a persistent single-host deployment, not ephemeral serverless storage.

To run serial payouts, configure a funded testnet-only `CAPTAB_EXECUTOR_ACCOUNT_ID` and `CAPTAB_EXECUTOR_PRIVATE_KEY`. Once a distribution is funded, a verified DAO council member can queue its ready or failed recipients from the company page; an internal caller can also POST `{ "companyId": "company.testnet" }` to `/api/distributions/<id>/execute` with `Authorization: Bearer <CAPTAB_WORKER_SECRET>`. The server reads the immutable entitlements from the contract, so request bodies cannot set recipients or amounts. The worker rechecks the chain before signing, records the transaction hash, waits for final receipt reconciliation, then advances to the next recipient. An ambiguous submission, mismatched attempt, or unresolved callback blocks the queue in `NeedsReview`; there is deliberately no timeout-based retry. A worker claim still unresolved after two minutes is marked `NeedsReview` for a possible process crash, appears on the activity page, and requires operator investigation before the queue resumes.

Set `CAPTAB_AUTH_ORIGIN` to the exact public origin used in the browser (`http://127.0.0.1:3000` for local development; HTTPS is required elsewhere). Private profiles use a five-minute NEP-413 challenge, a full-access key check against the NEAR account, and a twelve-hour HTTP-only session. The server reads the current Sputnik DAO council role for every private-profile request. Council members can save names and email addresses for on-chain stakeholders; other verified accounts see only their own saved profile. Wallets without NEP-413 `signMessage` support cannot use private profiles yet. The signature format follows the [NEP-413 specification](https://github.com/near/NEPs/blob/master/neps/nep-0413.md).

For sponsored claims, set a funded testnet-only `CAPTAB_RELAYER_ACCOUNT_ID` and `CAPTAB_RELAYER_PRIVATE_KEY`. The `/me` screen offers the option only when the connected wallet exposes delegated-action signing. The `/api/sponsor` endpoint accepts one serialized signed delegate action for `claim_vested(grant_id)` on the selected company, with zero deposit and at most 30 Tgas. It verifies the signature, account key, nonce, short expiry, and current claimable grant before the relayer signs an outer transaction. A digest uniqueness constraint and per-account/global rate limits prevent replay and unbounded fee spend. Ambiguous relay outcomes remain `NeedsReview`; do not resubmit the same signed delegate. This follows [NEP-366](https://github.com/near/NEPs/blob/master/neps/nep-0366.md). The Sandbox test proves the chain path from a zero-balance contributor; wallet compatibility and the complete API journey still need live testnet validation.

The ownership pages link to a cap table export at `GET /api/companies/<account>/export?format=csv` or `format=json`. The response carries `X-Captab-Ledger-Revision` and `X-Captab-Export-SHA256` headers, and returns 409 if the ledger revision changed during the read. The ownership page also has a priced-round model, and the distributions page has an exit waterfall preview. Both are client-side projections that submit nothing.
